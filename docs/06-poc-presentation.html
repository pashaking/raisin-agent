01 Donation AI Control Plane · proof of concept

Can an LLM assistant read donation data without ever becoming the thing that decides what it may see?

A runnable, 13-container control plane for a regulated multi-tenant donation platform. Real gateway (LiteLLM), real policy engine (OPA), real guardrails (NeMo Guardrails, an injection classifier, OpenAI moderation, Presidio), real providers, real RAG, one trace per request. Every decision that matters is made outside the model and shows up as a span.

03 System design

No stubs except the payment gateway, which is a stub on purpose so the "never AI" boundary is measurable. The mapping is deliberate: real components exercise real failure modes (model download, judge latency, provider 402).

1. The model never sees what it may not use.

OPA's model-stage decision returns allowed_tools; the runtime builds tool schemas from that list and nothing else. A Donor's model does not know get_donation exists. Retrieval gets the same treatment: OPA's retrieval_filter becomes the SQL WHERE on the vector search.

2. Every tool call is authorized twice, on the resource's tenant.

Runtime resolves the owning tenant of the id through a Policy Information Point, asks OPA with resource.tenant_id, then raisin-api re-checks service token, JWT role and tenant in SQL. Two independent layers must both be wrong.

3. PII is a placeholder from the moment it enters.

Presidio finds PERSON, EMAIL, PHONE, CREDIT_CARD; the runtime swaps them for tokens and keeps the mapping in memory. Model, gateway, provider, judge, Jaeger and Phoenix all see the token. Output carrying raw contact data that was not a placeholder is refused.

How it is wired

  • Policy as files: policy/authz.rego + tests, policy/data/roles.json (static), policy/data/registry.json (generated by seed from the ai_registry table and pushed to OPA over its data API).

07 Tool call authorization

Two independent layers must both be wrong for a cross-tenant read

The runtime holds no database credentials for the system of record. Every tool is a narrow HTTP call to raisin-api with two credentials: the caller's JWT (who is asking) and the runtime's X-Service-Token (proof the call came through the control plane).

Design points worth pointing at

  • Registry is live data, not a restart. Flip approved=false on get_donation, push, and the tool disappears from allowed_tools on the next request; policy.registry_revision changes on the span (scenario 6).
  • No masked email either. A first cut returned a***@example.com; Presidio blocked it, the reshaped "a*** at example.com" was blocked by the NeMo output rail. Allow-listing a masked shape would hand the model an exfiltration format, so the tool returns donor id and giving summary only.
  • Rails follow scope. Widening from single-transaction questions to lists and summaries made the self-check judge block ordinary questions; the rail prompt now distinguishes viewing from changing records, and test_tools.py keeps a regression list (9 allowed, 5 blocked phrases).
  • Model tool choice moved. With get_donation available, gpt-4o-mini prefers it over get_transaction_analysis for "why was X declined"; scenarios were re-pointed rather than the prompt forced.
08 Guardrail layers

Three stages, every hit named so the span explains itself

Input blocks hard (400). Retrieved chunks are flagged but still passed, because the classifier scores procedural runbooks as injections and the controls that actually hold are the tool-stage policy and the output scan. Output blocks soft (200 with a fixed refusal).

Why the output stage blocks raw PII when the input stage already placeholdered it.

A tool result or a hallucination can introduce an email or phone number the user never typed. Anything of those types that is not one of this request's placeholders is by definition data the model should not have produced.

Accepted trade-off: LLM-judged rails cost latency and are not deterministic.

Each NeMo self-check is a gpt-4o-mini call (0.5 to 4 s in captured traces); an assistant question with one RAG call makes about six judge calls. Classifier and moderation are the deterministic floor; NeMo is the layer that understands intent, and its prompts are a bind-mounted YAML so they are explainable and swappable.

09 The other two paths

Story generation keeps PII out of the provider; the payment path never sees AI

POST /story · Participant

Same skeleton as the assistant path with four differences.

  1. Prompt is story-generator-v1; OPA checks it is approved. Participant role has tools: [], so no schemas and no tool loop.
  2. Temperature fixed at 0.7. Model returns strict JSON {story, social_post}; the runtime parses the first {...} block and falls back to the whole reply as story.
  3. Output stage scans story + social_post together; a block returns {story: REFUSAL, social_post: ""}.
  4. Restoration differs per field. story gets every placeholder back. social_post is public: PERSON becomes first name only, and any sentence with a contact placeholder is dropped whole, so the post never reads "Contact me at or .".
Proof the provider never saw the PII.

Scenario 5 input: "My name is Jane Doe … call me at 604-555-0142 or email jane.doe@example.com". The chat span's input.value (with trace content on) reads My name is <PERSON_1> … call me at <PHONE_NUMBER_1> or email <EMAIL_ADDRESS_1>. The story comes back with "Jane Doe" restored; the social post has no phone or email.

POST /donate · public, never AI

No JWT (public form). raisin-api validates the tenant exists, upserts the donor without overwriting existing contact fields, takes the donation id from a database sequence (extra=forbid rejects a client-supplied id with 422), inserts a pending donation, calls payment-gateway /charge with {amount, currency, payment_token} only, records the transaction and updates the status.

PCI-scope property, asserted on real traces.

make test checks that at least one trace touches payment-gateway, at least one has a gen_ai.* attribute, and none has both. It also checks the canary donor's email and phone (used in scenario 0) appear in zero span attributes or events anywhere.

11 Observability

One trace per request, three destinations, no message content past the collector

Every Python service calls init_tracing(service_name); httpx and FastAPI instrumentation propagate traceparent. LiteLLM exports through its otel callback, OPA through distributed_tracing, NeMo through opentelemetry-instrument. The trace_id is returned in the JSON body and the X-Trace-Id header.

D. Operations and assurance

  • Evaluation harness in CI. Scenarios 0–9, the rail regression list and the trace assertions run on every change to prompts, rails, roles or registry, against a staging stack with synthetic tenants.
  • Registry governance. Approval workflow for models, tools and prompts (owner, risk tier, review date) in front of the ai_registry table; revision hash in every decision already gives the audit link.
  • Runbooks and alerts. Fail-closed means a control outage is a user-facing outage; alert on policy.reason=unavailable and guardrail.verdict=unavailable, with the same time-boxed RTO as the payment path.
  • Data retention. Traces carry no content by default, but enduser.id and tenant are identifiers; align trace and SIEM retention with PIPEDA and the PCI logging policy.
  • Tenant onboarding as one procedure. Tenant row → IdP claims → gateway key + budget → guardrail profile → KB ingestion. Today those are five hand edits; the tenant-c incident (missing env var, stale seed image) is the evidence.
14 Roadmap

What the POC proves, and the order to productionize it

Proven

  • Identity, not the prompt, decides tenant and role; OPA decides model, tools and retrieval scope; the runtime enforces and fails closed.
  • Cross-tenant reads need two independent layers to fail; a deny is invisible to the model as an oracle and visible to the SIEM.
  • PII never reaches a provider, a judge or a trace as a value; the payment path shares nothing with the AI path.
  • One trace per request across every service with cost, tokens, decisions and verdicts; content redaction enforced at two layers.
  • Provider swap is a config line (OpenAI and Anthropic both validated end to end).

Suggested order (maps to design 01, Phase 0–5)

1

Identity and secrets

Entra ID via JWKS, Secrets Manager, mTLS between services. Closes F7, F10, F11 and removes the largest stand-in.

2

Configuration to data

Gateway keys, roles, prompts, guardrail profiles and runtime settings out of code (section A). OPA bundles replace hand pushes.

3

Data isolation

RDS, separate roles, row-level security by tenant. Closes F4.

4

Platform

Terraform + ECS Fargate + ALB + Cloudflare/WAF; pinned images; CI evaluation harness. Closes F13.

5

Observability to the real SIEM

Managed tracing, SIEM exporter, alerting on unavailable and deny rates, retention policy.

6

Latency and cost

Judge caching, concurrent input checks, per-tenant rate limits, budgets owned by the business.
